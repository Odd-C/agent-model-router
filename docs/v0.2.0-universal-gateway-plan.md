## 1. 背景与问题

### 1.1 现状

- v0.1.0 已开源：MIT、Python 3.10+、**零第三方依赖**、50 tests passing
- 核心组件：`policy.py`（模型画像表 + 峰谷判断）、`quota.py`（5h 滑动窗口额度 + 失败冷却）、`router.py`（role 链驱动决策引擎）
- 核心 API：`recommend_for_session(text)` → `{model, provider, reason, tier, cost, difficulty, urgent, peak, key}`

### 1.2 诊断：引擎通用，接入形态单一

| 接入方式 | 现状 | 开源用户拿到后 |
|---|---|---|
| 库 API（`recommend_for_session()`） | ✅ 已有 | 需自己写集成代码，门槛高 |
| WebUI 前端集成（我们内部） | ✅ 内部有 | ❌ 仓库中不存在，等于"只能用于 WebUI" |
| **OpenAI 兼容代理层** | ❌ 缺失 | **把 `base_url` 指向调度器即可，零改码** |

**根因**：引擎层不依赖任何 WebUI 代码（纯决策，可单测），但**没有标准化的运行时接入层**。开源用户拿到的只是一个决策函数，无法直接当"模型网关"用。

### 1.3 目标

- 任何 OpenAI 兼容客户端（Hermes 各 profile / Claude Code / Codex / OpenClaw / 游戏 AI / 任意 SDK）**零改码**获得智能调度能力
- 保持零依赖卖点（纯标准库实现代理层）
- 修复包名不一致（pyproject 叫 `model-scheduler`，src 包却叫 `model_scheduler`）

### 1.4 非目标（v0.2.0 明确不做）

- 多租户/用户鉴权体系（第一版仅支持本机/localhost 绑定；对外暴露由使用方自行加反向代理鉴权）
- provider 主动健康探测（依赖失败冷却被动降级，够用且简单）
- 非 OpenAI 协议转换（如 Anthropic Messages API 直连——客户端侧用兼容层转换，不在本库范围）
- 请求级缓存 / 语义路由（保留给后续版本）

## 2. 架构设计

### 2.1 总体架构

```
任何 OpenAI 兼容客户端（Hermes / Claude Code / Codex / OpenClaw / 任意 SDK）
        │  base_url = http://127.0.0.1:8765
        ▼
┌──────────────────────────────────────────────────┐
│  model-scheduler serve（新增 server.py）           │
│                                                  │
│  POST /v1/chat/completions                       │
│    1. 解析请求（OpenAI 格式）                      │
│    2. 提取会话文本 → assess_difficulty / urgency  │
│    3. route_model() 选模型+provider               │
│    4. 改写 model / base_url / Authorization      │
│    5. 转发到目标 provider（标准库 urllib）          │
│    6. 响应回传（非流式 JSON / 流式 SSE 透传）       │
│    7. record_call() 记账；失败 record_failure()   │
│                                                  │
│  GET  /v1/models   列出当前可用模型                │
│  GET  /v1/health   健康检查                       │
└──────────────────────────────────────────────────┘
        │  转发
        ▼
  openai / deepseek / google / 任意 provider
```

### 2.2 部署形态（关键承诺）

**代理层是纯本地进程，不依赖任何外部调度服务/中心节点。**

- 运行位置：用户自己的机器（笔记本 / 服务器 / 容器均可）
- 决策与状态：难度评估、额度、峰谷、降级全部是库内逻辑 + 本地 `model-quota.json`，不出机器
- 网络：仅两条出向链路——用户机器 → 用户自己的 provider（转发）；客户端 → 本地代理（回环）
- 不收集任何遥测；不调用任何第三方 API（除用户配置的 provider 本身）
- 用户自备：真实 provider 的 API key + 自己的 `model-policy.json`（默认画像仅为机制演示）

> 与「库 API」的关系：代理层 = 库 API 的运行时封装。用户二选一或都用；代理层不是独立服务，是本仓库 `server.py` 模块，随 `pip install model-scheduler` 一起分发。

### 2.3 请求时序（非流式）

```
Client → Serve: POST /v1/chat/completions {model: "any", messages: [...], stream: false}
Serve:   text = 拼接 messages 内容
Serve:   decision = recommend_for_session(text)
Serve:   target = providers[decision.provider]  # base_url + api_key
Serve:   body.model = decision.model
Serve:   body 原样透传其余字段（tools/response_format/max_tokens...）
Serve:   POST target.base_url/chat/completions (Authorization: Bearer target.api_key)
Serve:   record_call(decision.model, decision.provider)   # 成功
Serve:   ← 2xx：透传 JSON 给 Client
         ← 4xx/5xx/超时：record_failure() → 进入冷却；透传错误给 Client
```

### 2.3 流式（SSE）处理

- 请求 `stream: true` 时，转发到目标 provider 后**逐块透传** SSE 事件（`data: {...}\n\n`）
- 不解析/不缓存流内容（保持低延迟），只在连接结束或出错时记账
- 转发失败 / 上游断开：向 Client 发送错误 SSE 事件并关闭

### 2.4 记账与冷却

- 成功：`quota.record_call(model, provider)` — 扣 5h 窗口额度
- 失败（HTTP >= 400、超时、连接错误）：`quota.record_failure(model, provider)` — 进入冷却（默认 COOLDOWN_SECONDS）
- 冷却期内 `_entry_available()` 返回 False → 路由自动跳过该模型，走降级链
- 免费额度耗尽 → 自动回退付费模型（现有逻辑，代理层零改动复用）

## 3. 接口规范

### 3.1 `POST /v1/chat/completions`

**请求体**（OpenAI Chat Completions 格式，`model` 字段可为任意值——实际模型由调度器决定）：

```json
{
  "model": "auto",
  "messages": [{"role": "user", "content": "帮我写一个 Python 脚本"}],
  "stream": false,
  "temperature": 0.7,
  "max_tokens": 2048
}
```

**响应**：透传目标 provider 的 OpenAI 格式 JSON；`stream: true` 时透传 SSE。

**特殊约定**：
- 客户端可传 `"model": "auto"` 让调度器全权决定；也可传具体模型名做**软提示**（后续版本支持"指定模型优先，不可用时降级"，v0.2.0 先忽略具体名，一律按调度决策）
- 响应中附加非标准字段（可选）：`x-model-scheduler: <decision.key>` 响应头，便于客户端观测实际路由结果

### 3.2 `GET /v1/models`

返回当前**可用**模型列表（排除冷却中/额度耗尽的免费模型）：

```json
{
  "object": "list",
  "data": [
    {"id": "gpt-4o@openai", "object": "model", "owned_by": "openai"},
    {"id": "gemini-2.0-flash@google", "object": "model", "owned_by": "google"}
  ]
}
```

### 3.3 `GET /v1/health`

返回 `{"status": "ok", "version": "0.2.0"}`，用于 systemd/容器健康检查。

## 4. providers 配置

`model-policy.json` 增加 `providers` 段（与现有 `models` 段平级）：

```json
{
  "language": "zh",
  "peak_hours": [[9, 12], [14, 18]],
  "providers": {
    "openai": {
      "base_url": "https://api.openai.com/v1",
      "api_key": "env:OPENAI_API_KEY"
    },
    "deepseek": {
      "base_url": "https://api.deepseek.com/v1",
      "api_key": "env:DEEPSEEK_API_KEY"
    },
    "google": {
      "base_url": "https://generativelanguage.googleapis.com/v1beta/openai",
      "api_key": "env:GEMINI_API_KEY"
    }
  },
  "models": {
    "gpt-4o@openai": { "...": "..." }
  }
}
```

**规则**：
- `api_key` 支持 `env:VAR_NAME` 引用环境变量（**禁止**明文写密钥进 JSON；支持直接写字符串做简单部署，但 README 明确警告）
- 缺少某 provider 配置时：该 provider 下所有模型视为**只决策不转发**（`/v1/models` 不展示、路由跳过）
- `base_url` 不含 `/v1` 后缀由实现容错（自动拼接 `/chat/completions`；含则直接用）
- providers 段缺失时：代理层启动失败并给出明确报错（因为没有 provider 就没法转发），库 API 不受影响

## 5. 包名对齐方案

### 5.1 现状问题

- `pyproject.toml` → `name = "model-scheduler"`（发布名）
- `src/` → `model_scheduler/`（import 名）
- 后果：`pip install model-scheduler` 后用户 `import model_scheduler` 失败，只能 `import model_scheduler`——**开源体验硬伤**

### 5.2 方案（推荐）：重命名 + 兼容别名

1. `git mv src/model_scheduler src/model_scheduler`
2. 所有文件内 `model_scheduler` → `model_scheduler`（import、docstring、测试路径）
3. `__init__.py` 提供兼容层：
   ```python
   # model_scheduler 兼容别名（v0.2.0 弃用警告，v0.3.0 移除）
   import sys, warnings
   sys.modules.setdefault("model_scheduler", sys.modules[__name__])
   ```
4. README / examples / tests 全部更新为 `import model_scheduler`
5. 可选：额外提供 `model_scheduler.py` 顶层 shim（`from model_scheduler import *` + DeprecationWarning），让旧代码平滑迁移

### 5.3 影响面

| 文件 | 改动 |
|---|---|
| `src/model_scheduler/*` → `src/model_scheduler/*` | 目录重命名 + import 替换 |
| `tests/*.py` | import 路径替换 |
| `examples/*.py` | import 路径替换 |
| `README.md` / `README.zh-CN.md` | 示例代码替换 |
| `pyproject.toml` | 无（name 已正确） |

## 6. 测试计划

### 6.1 单元测试（新增 `tests/test_server.py`，约 15-20 用例）

| 用例 | 验证点 |
|---|---|
| 请求解析 | messages 拼接 → difficulty 评估正确 |
| 路由改写 | 请求 model 被替换为决策结果 |
| 无 provider 配置 | 该模型被跳过/报错 |
| 成功记账 | record_call 被调用，额度递减 |
| 失败记账 | 4xx/5xx → record_failure → 冷却 |
| 冷却期跳过 | 冷却中模型不出现在 /v1/models、路由绕过 |
| /v1/models | 只列可用模型 |
| /v1/health | 返回 ok |

### 6.2 集成测试（`tests/test_server_integration.py`）

- 用标准库起一个 **mock provider**（本地 http.server，返回固定 OpenAI 格式响应）
- 起真实 `server.py` 代理（端口 0 自动分配）
- 全链路验证：
  1. 非流式：curl 等价请求 → mock provider 收到改写后的请求 → 客户端收到透传响应
  2. 流式：`stream: true` → mock 分块返回 SSE → 客户端逐块收到
  3. 失败降级：mock provider 返回 429 → 记账冷却 → 再次请求路由到其他 provider

### 6.3 回归

- 现有 50 tests 全量保持通过
- `python -m pytest tests/ -q` 绿色收尾

## 8. 风险与边界

| 风险 | 等级 | 缓解 |
|---|---|---|
| SSE 透传兼容性（不同 provider 事件格式差异） | 中 | 逐块透传不解析；集成测试覆盖 mock SSE；README 标注"流式透传不保证全 provider 语义一致" |
| 请求体改写遗漏（tools/response_format 等新字段） | 中 | 白名单改写：只动 model + headers，其余字段原样透传 |
| provider 响应格式差异（非标准 OpenAI 字段） | 低 | 透传为主，不解析业务字段 |
| 多实例并发写 quota 文件 | 低 | 现有 `atomic_write_json` 线程安全 + 原子写；单实例默认 |
| 端口冲突 / 常驻进程管理 | 低 | systemd 示例 + `--host/--port` 参数；非本仓库核心 |
| 零依赖约束（不用 fastapi/httpx） | 中 | 用 `http.server.ThreadingHTTPServer` + `urllib.request`，标准库可胜任；如遇阻塞问题再评估（会提前报备，不悄悄加依赖） |

## 9. 接入示例（README 展示）

### 9.1 代理层（零改码）

```bash
pip install model-scheduler
export OPENAI_API_KEY=sk-xxx DEEPSEEK_API_KEY=sk-xxx
model-scheduler serve --config model-policy.json --host 127.0.0.1 --port 8765
```

任意 OpenAI 兼容客户端：

```bash
# curl 示例
curl http://127.0.0.1:8765/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"写个快排"}],"stream":true}'

# OpenAI SDK 示例
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8765/v1", api_key="unused")
resp = client.chat.completions.create(model="auto", messages=[...])
```

### 9.2 库 API（程序内集成）

```python
from model_scheduler import recommend_for_session, record_call
decision = recommend_for_session(user_text)
# 自行用 decision.model / decision.provider 发请求
record_call(decision.model, decision.provider)
```

## 10. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 代理层进主仓库（非独立仓库） | 引擎 + 网关是同一产品，版本同步、依赖同源 |
| D2 | 零依赖约束保持 | 核心卖点；标准库足以实现 |
| D3 | 包名重命名 + 兼容别名 | v0.1.0 刚发，无外部用户，现在改成本最低 |
| D4 | providers 密钥走 `env:` 引用 | 安全底线（不硬编码密钥） |
| D5 | 失败冷却复用现有 quota 机制 | 引擎零改动，代理只加调用 |
